# COMPARISON — наш пайплайн vs Docling vs DeepDoc (RAGFlow)

> Дата: 2026-10-16. Контекст: обоснование преп-пайплайна «рус. PDF →
> качественный и производительный MD» — потребители Obsidian (человек) и
> RAG/БЗ Cherry Studio; железо локальное (Strix Halo, llama.cpp/Vulkan, без
> CUDA). QC-гейт — средство гарантии качества MD, не самоцель.
> Источники: репо/доки проектов на дату (docling-project/docling,
> infiniflow/ragflow `internal/deepdoc`), OmniDocBench, наши приёмочные прогоны
> (USAGE §3.5–3.6). Сопроводительное обсуждение — сессия opencode 2026-10-16.

## 1. Сводная таблица

## 2. Детали

### 2.1 Docling — сильное / слабое
- **Сильное:** форматная широта (лучший вариант для DOCX/PPTX/XLSX/HTML/EPUB),
  полностью MIT, экосистема (serve-API, MCP, chunking, интеграции), TableFormer
  на чистых цифровых таблицах, активная разработка (IBM/LF AI).
- **Слабое для нас:** на Strix Halo — CPU-only (нет CUDA; ROCm gfx1151 не
  поставляется в wheels); layout/таблицы обучены на англ. корпусах;
  GraniteDocling на кириллице под вопросом + повторы; нет QC-гейтов и нашей
  обвязки — т.е. ~70% ценности нашего пайплайна пришлось бы дописывать.

### 2.2 DeepDoc — сильное / слабое
- **Сильное:** позиционное мышление (блоки с координатами → точный citation в
  retrieval), TSR-таблицы, офисные форматы, Apache-2.0 всё, интеграция в
  полный RAG-стек (чанкеры, индексы, поиск) — если нужен не преп-пайплайн,
  а готовая RAG-платформа.
- **Слабое для нас:** не самостоятельный продукт — использовать = перейти на
  RAGFlow целиком (замена Cherry Studio, другой проект); кириллических
  OCR-моделей нет (zh/en), OUR DoLA/TSR-модели не рус.; onnxruntime → CPU на
  нашей машине; на выходе чанки RAGFlow, а не чистый MD; нет QC.
  Ист.: репо infiniflow/ragflow, `internal/deepdoc/` (Go, det/rec/tsr/dla,
  session-пул ONNX Runtime), 2026-10.

### 2.3 Наш пайплайн — сильное / слабое
- **Сильное:** единственный из трёх заточен под наш кейс — качественная и
  производительная конвертация рус. PDF в MD (два потребителя: Obsidian и RAG);
  QC-гейт (главная ценность — «не пустить мусор в БЗ»); Vulkan-инференс на
  AMD без CUDA; VLM-captioning фигур локальной 35B; фрагменты/склейка/resume/
  ETA; приёмка на реальных документах с битыми шрифтами (README §1).
- **Слабое:** один формат (PDF); ореховая связка на llama.cpp 0.6.0-dev
  (грабля upstream с grammar, см. HANDOFF); веса surya OpenRAIL-M;
  обвязка самописная — поддержка на нас.

## 3. Вердикт

1. **Как замена основного пути — не подходит ни Docling, ни DeepDoc:**
   оба упираются в наше железо (CPU-only) и в русский язык (модели/гейты);
   ни в одном нет QC-обвязки — смысла нашего проекта.
2. **Docling** — уже стоит в README §2 как «запасной вариант»; практическая
   ниша — конвертер **не-PDF форматов** (DOCX/PPTX/XLSX/HTML/EPUB → MD)
   в наш же inbox/outbox с нашим QC-гейтом (кандидат-задача).
3. **DeepDoc** — имеет смысл только при миграции с Cherry Studio на RAGFlow
   как платформу (чанки/citation из коробки); это смена концепции БЗ, а не
   апгрейд преп-пайплайна. Для текущей цели — не конкурент.

**Уточнение кейса (2026-10-16):** MD потребляют двое — Obsidian (человек) и
RAG (Cherry Studio). Это добавляет ось «читабельность MD человеком» и не меняет
вердикт: marker выдаёт чистый MD с относительными ссылками на картинки
(каталог результата = папка в хранилище Obsidian), VLM-описания фигур работают
одновременно как alt-текст для человека и как текст для находимости в RAG;
Docling/DeepDoc на выходе дают либо «документ для машины» (чанки/DocTags),
либо MD без наших гарантий качества.
