# Открытые OCR-модели: альтернативы Surya OCR 2 в контексте AMD Strix Halo

**Дата:** 2026-10-14
**Вопрос:** какие открытые модели — аналоги или лучше surya-ocr-2, и как они ложатся на текущее окружение (Strix Halo: Ryzen AI Max 395+, Radeon 8060S, 128 ГБ единой памяти, Linux/ROCm/Vulkan, без CUDA).

> Метод: веб-поиск был недоступен, данные собраны прямыми загрузками README первоисточников (GitHub) 2026-10-14. Цифры бенчмарков принадлежат разным методикам и между собой напрямую не сравнимы (см. §5). Оценки скорости на Strix Halo — ориентировочные экстраполяции, не измерения.

## 1. Резюме (TL;DR)

| Если нужно… | Кандидат | Почему |
|---|---|---|
| Максимальная точность среди специализированных открытых | **dots.mocr** (3B) | Лучший specialized на olmOCR-bench (83.9) и OmniDocBench v1.5 (TextEdit 0.031), Elo выше PaddleOCR-VL-1.5; но CUDA/vLLM-центрична → на Strix Halo только transformers+ROCm, медленно и хлопотно |

## 2. Базовая точка: Surya 2 (datalab-to/surya)

- **Архитектура:** один VLM ~650M параметров (в духе Qwen3.5) на всё — OCR, layout, порядок чтения, распознавание таблиц; детекция строк — отдельная torch-модель.
- **Точность:** 83.3% на olmOCR-bench (лучший результат среди моделей <3B по заявлению Datalab); 87.2% прохода на внутреннем бенчмарке 91 языка; русский — в таблице топ-15 языков.
- **Скорость:** ~5 стр/с на RTX 5090 (у них это «ориентир верхнего края»).
- **Запуск:** vLLM (только NVIDIA) **или llama.cpp** (официально «CPU / Apple Silicon»; Vulkan-сборка llama.cpp задействует и 8060S — не заявлено, но механика общая). Детекция — чистый torch.
- **Лицензия:** код Apache-2.0; веса — модифицированный AI Pubs OpenRAIL-M (бесплатно для исследований, личного использования и стартапов с оборотом/финансированием до $5M).
- **Вывод для SH:** рабочая; апгрейд-причины искать в (а) точности на русском, (б) таблицах/формулах, (в) скорости на iGPU.

## 3. Окружение Strix Halo: что важно для OCR-моделей

Железо/софт-факторы, определяющие совместимость:

1. **Нет CUDA → нет vLLM.** vLLM не поддерживает gfx1151. Все модели, чей основной путь — «vllm serve …» (dots.mocr, DeepSeek-OCR, olmOCR, Chandra в рекомендованном режиме), на SH запускаются лишь через transformers+ROCm, с потерей скорости и отладкой на свою ответственность.
2. **ROCm для APU — отдельный трек.** gfx1151 отсутствует в основной таблице Supported GPUs (Instinct/Radeon dGPU); для Ryzen APU существует ветка «Use ROCm on Radeon and Ryzen» с собственным инсталлятором («Ryzen software for Linux with ROCm») и PyTorch для Ryzen APU (документация трека покрывает версии до 7.2.1, с ROCm 7.13+ документация объединена с основной). Альтернатива — ночные сборки TheRock. Итог: PyTorch на SH — рабочий, но «второй класс» по сравнению с NVIDIA; проверять совместимость колёс под каждую версию.
3. **llama.cpp Vulkan — родной путь для 8060S.** Именно он официально выбран: MinerU 4.0 (бэкенд по умолчанию), HunyuanOCR-1.5 (GGUF из коробки), Surya 2 (один из двух бэкендов). Всё, что есть в GGUF, — запускается.
4. **128 ГБ единой памяти.** Помещается всё вплоть до Chandra 2 (~11B bf16 ≈ 22 ГБ + KV) с запасом; конкуренция за память с ОС минимальна при UMA-аллокации 32–64 ГБ (до 96 ГБ). Это реальное преимущество SH против бытовых GPU с 8–16 ГБ.
5. **Узкое место — пропускная способность (~256 ГБ/с, делится CPU+iGPU) и отсутствие «нвидиевских» тензорных ускорителей FP8/FP4.** Поэтому decode больших VLM медленнее, чем на RTX 4090/5090; конвейерные модели (детекция+распознавание, ONNX) страдают меньше.
6. **NPU (XDNA2, ~50 TOPS) перечисленными стеками не используется** — не фактор выбора.
7. **16 ядер Zen 5** дают приличный CPU-путь: ONNX-конвейеры (PP-OCRv6 с OpenVINO) и llama.cpp-CPU работают достойно.

## 4. Каталог альтернатив

### 4.1 dots.mocr (ex dots.ocr-1.5) — rednote-hilab / studio-dots-ai
- **Что:** 3B мультимодальная модель разбора страниц (текст/строки/формулы/таблицы, вкл. межстраничные таблицы); плюс отдельная dots.mocr-svg — диаграммы/графика → SVG. Заявка на «практически любую письменность»; русский — в витрине примеров.
- **Цифры (из их README, оценка Elo — судья Gemini 3 Flash):**
  - olmOCR-bench: **83.9±0.9** (выше Chandra 1 — 83.1, olmOCR v0.4.0 — 82.4, PaddleOCR-VL — 80.0, MinerU 2.5.4 — 75.2, DeepSeek-OCR — 75.7);
  - OmniDocBench v1.5: TextEdit **0.031** / ReadOrderEdit **0.029** — лучший из перечисленных (PaddleOCR-VL(-1.5): 0.035/0.042; MinerU2.5: 0.047/0.044; DeepSeek-OCR: 0.073/0.086);
  - Elo (среднее по 3 бенчмаркам): **1124.7** — лучший специализированный; PaddleOCR-VL-1.5 — 920.5, HunyuanOCR — 984.2; Gemini 3 Pro (закрытый) — 1210.7.
- **Запуск:** vLLM или transformers (`device_map=auto`, `.cuda()`) — CUDA-центрично; GGUF официально не заявлен.
- **Лицензия:** в README не указана явно (v1 dots.ocr была Apache-2.0) — проверить перед внедрением.
- **На SH:** по точности — главный «лучше surya»; по запуску — самый неудобный из лидеров (transformers+ROCm, ~3B).

### 4.2 PaddleOCR-VL-1.6 (+ PP-OCRv6) — PaddlePaddle, Apache-2.0
- **Что:** семейство: PaddleOCR-VL-1.6 — 0.9B VLM (NaViT-энкодер + ERNIE-4.5-0.3B) для полного разбора страницы в Markdown/JSON; PP-OCRv6 — классический лёгкий конвейер (детекция+распознавание), три размера: tiny 1.5M / small 7.7M / medium 34.5M.
- **Цифры:** PaddleOCR-VL-1.6 — **96.3% на OmniDocBench v1.6**, заявленное лидерство в тексте/формулах/таблицах (v1.5 была 94.5% на v1.5-бенче); 111 языков (v1.5) вкл. **русский (кириллица)**; PP-OCRv6: +4.6% детекция / +5.1% распознавание против PP-OCRv5_server, **5.2× ускорение на CPU** (OpenVINO), 0.13 с/стр на A100; PaddleOCR-VL v1 — 80.0 на olmOCR-bench.
- **Запуск:** Paddle Inference / **transformers (с версии 3.5.0 для 20 моделей)** / ONNX-экспорт / OpenVINO — максимально переносимый набор бэкендов.
- **На SH:** лучший баланс «точность + русский + переносимость»: VL через transformers+ROCm; PP-OCRv6 — быстрый CPU-конвейер. Отдельно вышел HPD-Parsing (07/2026) — высокопроизводительный парсер (до 4752 ток/с) под vLLM.

### 4.3 MinerU 4.0 — OpenDataLab
- **Что:** не одна модель, а комбайн: парсинг PDF/изображений/Office/EPUB/HTML → Markdown/JSON, локальная библиотека документов, сервер, агентский CLI; 4 уровня качества (flash/basic/standard/advanced); Office-форматы парсит нативно (flash), без OCR.
- **Ключевое для SH — политика бэкендов по умолчанию:** «малые модели — ONNX CPU, VLM — **llama.cpp в режиме Vulkan**, хорошая совместимость с большинством устройств»; в таблице железа есть строка «Linux/Windows with modern iGPU»; basic = ONNX + llama.cpp (CPU работает, Vulkan рекомендован); standard = + PyTorch; advanced = + vLLM/lmdeploy/mlx (нужна NVIDIA 8GB+ VRAM или Apple MPS).
- **Точность (их конвейер 2.5):** 75.2 на olmOCR-bench (2.5.4); MinerU2.5 (1.2B): TextEdit 0.047 на OmniDocBench v1.5.
- **Лицензия:** «MinerU Open Source License» — Apache 2.0 с дополнительными условиями (проверить текст).
- **На SH:** самый беспроблемный старт — ставится и работает на iGPU без ручной сборки стека; точность конвейера — середина верхней группы.

### 4.4 HunyuanOCR-1.5 — Tencent Hunyuan
- **Что:** лёгкая (0.9B) сквозная OCR-VLM; версия 1.5 (07/2026) сделана ради скорости: DFlash speculative decoding, «Agentic Data Flow», обновлённый рецепт обучения.
- **Ключевое для SH:** **официальная поставка GGUF (base + mmproj) и развёртывание через llama.cpp/llama-server** с OpenAI-совместимым API — целевой сценарий «CPU / consumer-GPU / laptop»; DFlash влит в апстрим llama.cpp. Плюс пути vLLM и transformers для серверного режима.
- **Цифры:** Elo-среднее 984.2 (второй среди специализированных в таблице dots); CHAOS-Bench (их бенчмарк галлюцинаций на уровне символов) — из их экосистемы.
- **Лицензия:** Tencent Hunyuan Community License (не OSI; условия — из репозитория, проверить применимость).
- **На SH:** один из двух наиболее «родных» вариантов (GGUF+Vulkan); акцент на скорость и устойчивость к галлюцинациям.

### 4.5 Chandra OCR 2 — Datalab (старший брат Surya)
- **Что:** «State of the art» OCR от того же автора: изображения/PDF → HTML/Markdown/JSON с полной разметкой; сложные таблицы, формы с чекбоксами, рукопись, 90+ языков; «возглавляет внешний olmOCR-benchmark» (по их замерам на H100; ~2 стр/с в реальных задачах на H100).
- **Запуск:** vLLM (рекомендован) или HF transformers (torch). Размер: серия на базе Llama-3.2-Vision, Chandra 1 — 11B; точный размер Chandra 2 в README не указан — считать «~11B, проверить».
- **Лицензия:** код Apache-2.0; веса — модифицированный OpenRAIL-M (бесплатно до $2M оборота/финансирования; запрет конкурировать с их API); **коммерческий селф-хостинг — платная лицензия**.
- **На SH:** влезает в 128 ГБ с запасом; но ориентация на vLLM/H100 и «тяжёлая» архитектура делают его кандидатом «на вырост», а не на повседневную скорость.

### 4.6 olmOCR 2 (v0.4.0) — Allen AI, Apache-2.0
- **Что:** 7B VLM (тонкая настройка Qwen2.5-VL), PDF → чистый Markdown/текст; 82.4 на olmOCR-bench; модель по умолчанию FP8.
- **Запуск:** пайплайн на vLLM + CUDA 12.8 + flashinfer; заявленные требования — NVIDIA с ≥12 ГБ VRAM. Для SH — несобираемое окружение; теоретический обход — взять базовую Qwen2.5-VL-7B GGUF в llama.cpp и промптить самостоятельно (уже не olmOCR-пайплайн).

### 4.7 DeepSeek-OCR / DeepSeek-OCR2
- **Что:** 3B MoE-модель «оптического сжатия контекста» (изображение → компактные токены текста); 75.7 на olmOCR-bench; OmniDocBench v1.5 TextEdit 0.073. 2026-01-27 анонсирован DeepSeek-OCR2 (отдельный репозиторий; здесь не изучался — проверить отдельно, если интересен).
- **Запуск:** vLLM или transformers; эталонное окружение cuda11.8+torch2.6 — CUDA-центрично.
- **На SH:** только самодельный transformers+ROCm; как парсер документов уступает специализированным лидерам.

### 4.8 Кратко: замеченные в бенчмарках, но не разобранные
GLM-OCR (0.9B, Zhipu), MonkeyOCR-pro-3B, OCRVerse-4B, Infinity-Parser-7B (82.5 на olmOCR-bench), Nanonets-OCR2-3B, LightOnOCR-2-1B (фигурирует в сравнении surya). Кандидаты для отдельной проверки, если лидеры не устроят.

## 6. Как читать бенчмарки (честные оговорки)

1. **olmOCR-bench** (Allen AI) — англо-центричен, «трудные» PDF; **OmniDocBench** (v1.5/v1.6, OpenDataLab) — существенно китайско-центричен; **Elo-таблицы** (dots) — LLM-судья (Gemini 3 Flash), чувствителен к промпту и формату вывода.
2. Сравнивать модели **только внутри одного бенчмарка**; «83.9 в olmOCR-bench» и «96.3% в OmniDocBench v1.6» — несопоставимые величины.
3. Таблицы в README dots.ocr — компиляция вендора (в т.ч. их собственной модели); цифры surya/chandra — компиляция Datalab. Независимой консолидированной таблицы в этом обзоре нет (веб-поиск был недоступен).
4. **Для русского языка** публичных детальных цифр почти нет у всех; финальный выбор стоит проверять на собственном корпусе (ваш кейс — русскоязычные стандарты/ГОСТ-подобные документы с таблицами).

## 7. Рекомендации по сценариям (это железо)

1. **Быстрый апгрейд точности без смены стека:** попробовать **HunyuanOCR-1.5 GGUF** (тот же llama.cpp/Vulkan, что и текущий путь surya) и **PaddleOCR-VL-1.6** (transformers+ROCm; PyTorch для Ryzen APU из трека ROCm on Radeon and Ryzen). Прогнать оба на 20–50 своих страницах против surya.
2. **Максимальная точность, готовы повозиться:** dots.mocr через transformers+ROCm (vLLM на gfx1151 нет); замерить, выдерживается ли приемлемая скорость на 3B.
3. **Полный конвейер «поставил и работает»:** MinerU 4.0 в дефолтной конфигурации (ONNX + llama.cpp Vulkan) — единственный из лидеров, для кого iGPU — заявленный целевой класс железа.
4. **Пакетная скорость на CPU / фоновые задачи:** PP-OCRv6 (ONNX/OpenVINO).
5. **Не тратить время на OLmOCR/DeepSeek-OCR** в их основных пайплайнах — они спроектированы под NVIDIA/vLLM.
